# Обязательное сохранение в форк

## Договор
GitHub — основной источник тренировочного состояния. Для Дани:
repository_full_name=dke568/personal-trainer-skill, branch=main,
entrypoint=coach-data/danya/CURRENT.md. Настройка хранится в storage.json.
Новый чат читает свежую удалённую версию, не выбирает старую сводку из памяти.
Публичный код и спортивные записи разрешены владельцем. Медицинские документы,
секреты, приватные ссылки и клинический профиль автоматически не публиковать.
Если для вопроса нужен приватный контекст, читать его отдельно; не давать старой
приватной сводке перезаписывать более новые тренировочные данные GitHub.

## Когда запись обязательна
Сразу после новой фактической тренировки/подхода/замера, исправления факта,
изменения цели, расписания, предпочтения или плана, влияющего на дальнейшую работу.
Не ждать конца чата, недели или отдельной просьбы «запиши». Авторизация владельца
на такие тренировочные записи постоянная. Не спрашивать подтверждение повторно.
Обычный вопрос о физиологии без новых данных и изменений не требует записи.

Предложение сохранять как proposed/plan; принятие плана не является выполнением.
Пользовательское предположение не становится подтверждённым фактом.
Неподтверждённое исправление записывать отдельным предложением/вопросом;
не заменять фактическое событие до разрешения неопределённости.

## Что сохранять вместе
- events.jsonl: новые факты и планы с источником, датой и статусом.
- changes.jsonl: каждую корректировку, причину, статус, источник и связи с событиями.
- profile.json / programme.md: актуальные проекции только при нужном изменении.
- decisions.md: обоснование и критерий пересмотра, дополнением к истории.
- checkpoint.json, CURRENT.md и handoff.md: последнее изменение, неопределённости
  и следующий шаг. Дата записи не обновляет автоматически дату старого замера.

Все связанные изменения публиковать одним атомарным коммитом.
История не удаляется; ошибки исправлять через supersedes. Файлы текстовые.
CURRENT.md — вход, а не замена первичным событиям.

## Порядок GitHub
1. Через подключение GitHub получить repo, текущий ref ветки и commit/tree.
   Проверить владельца/репозиторий/ветку. При работе локально сначала fetch.
2. Читать файлы строго на полученном SHA, а не смешивать версии main.
   Снимок включает config, head, tree, files. Ключи files — полные пути.
   Нужны profile.json, programme.md, events.jsonl, decisions.md, handoff.md,
   storage.json, а после первой записи также changes.jsonl, checkpoint.json,
   CURRENT.md. Пропавший обязательный файл не считать пустым журналом.
3. Сформировать change с постоянным уникальным id, recorded_at, source,
   kind, status, summary, reason, next_step, open_questions, events, updates,
   publication_scope=training_only. Исправление факта должно ссылаться на
   прежнее активное событие через supersedes. Не менять ID при сетевом retry.
4. Запустить scripts/fork_diary.py prepare --snapshot ... --change ... --out ... .
   Это только prepared_not_saved. Скрипт не содержит сети/токенов и не публикует.
   Замены profile/programme требуют before_sha256 прежнего содержимого.
5. Создать GitHub tree с base_tree_sha исходного дерева и подготовленными
   path/mode/type/content. Не пересобирать дерево с потерей чужих файлов.
   Создать commit с единственным parent=expected_head. Обновить main через
   update_ref(expected_sha=expected_head, force=false). Не force-push.
6. Прочитать commit, полный recursive tree и ref обратно через GitHub.
   Запустить verify с этими полными ответами. Проверяются SHA, repo/ref/type,
   mode, изменённые и сохранённые файлы тренировочного состояния.
7. Только после verified_saved сообщить кратко «Сохранено в дневник» и дать
   ссылку на запись/коммит, когда она полезна. Локальный файл или созданный
   объект commit без успешного обновления ветки не равен сохранению в форке.

## Конфликт или неизвестный исход
Если ref изменился, перечитать свежий снимок и заново применить исходную
корректировку. before_sha256 и supersedes проверяют смысловую совместимость.
При конфликте фактов не затирать новые данные; показать конкретное расхождение.
Не более трёх попыток публикации без нового решения. Не дублировать записи.
Если после сбоя change.id уже присутствует с тем же payload в свежем удалённом
журнале и состояние проходит проверку, повторная запись не нужна.
already_recorded_in_snapshot не является доказательством удалённой записи,
пока происхождение и свежесть снимка не проверены реальным чтением GitHub.
Если verify обнаружил уже продвинутую ветку, не откатывать её: перечитать
текущий журнал и проверить наличие изменения, сохранившегося в истории.

При недоступности записи прямо назвать, что НЕ сохранено. Дать pending change
с ID и содержимым для повторения. Не заменять это обещанием «я запомнил».
Не публиковать локальную очередь автоматически после изменения смысла данных.

## Инициализация
Только для явно разрешённого первоначального подключения допускается
bootstrap_storage=true при отсутствии storage.json и changes.jsonl.
Это создаёт конфигурацию в том же атомарном изменении; не симулирует, будто
файл уже существовал в удалённом снимке. В рабочем дневнике отсутствие
конфигурации требует проверки, а не повторной автоматической инициализации.

## Пределы
Никакой текст инструкции не гарантирует наличие GitHub-инструментов в новом
чате. Если доступа нет, честно обозначить ограничение. GitHub-история и проверки
целостности не заменяют независимые резервные копии или клиническую оценку.
